# v0.3.0 — Passport

**Released:** 2026-09-17

A TrustPass ID now resolves to a page anyone can read. That page states what has
been checked and, more carefully, what has not.

This page describes only what the `v0.3.0` tag contains. Later work belongs in
[`CHANGELOG.md`](../../CHANGELOG.md) under Unreleased.

## What's new

### The public read surface

- **`GET /passports/{trustpassId}`** — a separate prefix from `/products`, and
  not for tidiness. `POST /products` returns the whole serial; the same prefix
  returning a masked one on read is an asymmetry waiting to cause a mistake.
  When authentication arrives (TP-141), `/products/*` locks and `/passports/*`
  stays public — a prefix rule instead of a per-method exception.
- **No internal key ever crosses the boundary.** The repository projects named
  columns, so `product.id`, `product.issuerId` and `issuer.id` never leave
  Postgres. ([ADR 0005](../adr/0005-internal-keys-are-not-public.md))
- **A draft product has no passport.** A draft is a row that claims nothing, and
  publishing its passport would publish a claim nobody made. It returns 404.

### The passport page

Four outcomes, rendered distinctly and never confused:

| What happened | Status | What the reader is told |
| --- | --- | --- |
| The passport exists | 200 | The passport |
| One character was mistyped | 200 | "This code has a typo — **this does not mean the product is unregistered**" |
| Well-formed, never issued | 404 | "No passport for this code" |
| Not a TrustPass code | 200 | "This isn't a TrustPass code" |
| TrustPass unreachable | 200 | "**No check has been made**, so nothing about this product — good or bad — should be read from this page" |

The last two rows are the ones that matter.

A 404 for a mistyped code would be the system agreeing that the product is
unregistered because someone misread one character. That is a false fraud
accusation, and preventing it is why [ADR 0004](../adr/0004-trustpass-id-format.md)
spends a symbol of the identifier on a checksum. This release is where that
machinery first pays for itself.

And a passport-shaped layout with blank fields, served while the API is down,
reads as a product with nothing verified about it. An outage must not look like
a verdict.

### What has been checked, stated one claim at a time

Per [ADR 0003](../adr/0003-identity-is-not-authenticity.md), claims are surfaced
separately and never collapsed into a single badge.

| Claim | State | Why |
| --- | --- | --- |
| Issuer | verified / pending / unverified / suspended | a real column, backed by a national registry check |
| Serial | **recorded** | the issuer supplied it; nothing compared it to any object |
| Secure tag | not present | no NFC yet (`TP-EPIC-13`, unscheduled) |
| Warranty | nothing on record | no warranty table yet (TP-040+) |
| Physical product | **not independently verified** | permanent: a ledger cannot inspect an object |

The second row is the whole argument. "Serial: VERIFIED" would be a lie — it was
*recorded*, not checked. That one word is the difference between this project
and a green checkmark.

There is **no aggregate verdict and no trust score**. A score mixes identity,
provenance, warranty and condition into one number and invents a precision none
of them have.

Two states are shown as banners above everything else, because they invert what
the rest of the page means: an **unverified issuer** (everything below is that
company's own word) and a **suspended product** (something has been reported
about this specific unit).

### The serial

Shown as its last four characters, and only when at least five remain hidden.
Below that, nothing is shown — masking that discloses half the value is not
masking.

A buyer holding the product can confirm the match. Someone who scraped the QR
from a marketplace photograph learns nothing they could use to impersonate the
product or claim against its warranty.

The whole serial has no field on the type that reaches the page, so it cannot be
rendered by mistake rather than merely being left out.

### The QR

- Rendered inline on the passport as server-side SVG elements — no second
  request, no client JavaScript, no cross-origin problem.
- Also served as a file at `/trustpass/{trustpassId}/qr.svg` for an issuer who
  needs one to print.
- Black on white in both colour schemes. An inverted QR is rejected by a large
  share of scanners.
- Beside it, the page says that scanning it proves only that someone had the
  code. A QR can be photographed from a listing and reprinted onto any object.

Both surfaces come from one function over a zero-dependency encoder. That
encoder's default byte handling silently truncates non-ASCII — `中` becomes an
ASCII hyphen, with no error, producing a code that scans cleanly to a different
URL. This release refuses to encode anything it would corrupt.

## Verification

Beyond the 283 automated tests: a production build served against a real
database, with the passport, the typo page, the not-found page, the unreadable
page and both QR surfaces fetched over HTTP and checked. The QR matrices were
decoded by `jsqr` — a decoder unrelated to the encoder that produced them.

Every protective guard in this release was broken on purpose to confirm its test
fails. One did not: a quiet-zone test asserted the margin against the value
under test, so it passed with no margin at all. It was rewritten against the
specification's literal minimum.

## Known limitations

- **No authentication.** Anyone who can reach `POST /products` can register
  against any issuer. The API must not be exposed publicly before TP-141.
- **The 404 page renders no HTML**
  ([#38](https://github.com/clevervi/trustpass/issues/38)). The status is
  correct, but Next 16.3.5 leaves the not-found boundary for the client to
  render, so a reader without JavaScript sees a blank page. Measured across four
  configurations against a production build.
- **The QR has not been scanned by a physical phone.** Decoding its matrix
  proves the encoding is correct; it does not prove compatibility across camera
  apps and print sizes.
- No warranty, lifecycle events or ownership transfer. Those are v0.4.0 and
  v0.5.0.

## What this does not claim

TrustPass records who made each claim about a product and what it has checked.
It is not a certificate of authenticity, and nothing in this release renders one.
